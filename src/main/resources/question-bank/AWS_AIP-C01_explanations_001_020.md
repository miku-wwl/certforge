## Question 1

### 中文

#### 考点背景

本题考的是“公平性评估”和“安全过滤”不能混为一谈。推荐结果按人口群体拆分后，需要真正计算偏差、公平性或群体间差异；仅仅统计 API 延迟、被 Guardrail 拦截的次数，无法回答“某个群体是否得到更差推荐”。两个 Prompt 方案还必须在同一套指标上比较，才能知道是 Prompt 本身造成了差异，还是流量、数据或调用量不同。

题干同时给出实时监控、15% 阈值告警和每周比较报告。考试中的关键是优先选择能产生偏差指标的托管评估能力，再把指标接到 CloudWatch 的告警、仪表板和报告链路。SageMaker Clarify 承担评估与分组分析，CloudWatch 承担可观测和通知；这比自己解析每次模型输出更少代码，也更容易保持两个 Prompt 的口径一致。

#### 场景比喻

像质检员分别统计红、蓝、绿三条生产线的次品率，再把结果接到工厂警报器和周报系统；警报器响了，不等于它自己完成了公平性统计。

#### AWS 服务角色

| AWS 服务 | 角色比喻 | 在本题中的作用 |
|---|---|---|
| Amazon SageMaker Clarify | 分组质检员 | 分析不同人口群体的偏差与公平性指标，并比较 Prompt 方案 |
| Amazon CloudWatch | 仪表盘与警报器 | 接收指标，按超过 15% 的阈值告警并展示趋势 |
| Amazon Bedrock | 推荐发动机 | 对两套 Prompt 生成商品推荐结果，提供被评估的输出 |
| CloudWatch 报告链路 | 周报编辑 | 汇总两种方案的指标，支持周期性比较 |

#### 正确答案与推理

1. 先看核心名词：题目要的是 demographic fairness，而不是内容安全或基础设施健康度。
2. Clarify 能按群体分析模型输出并形成偏差、公平性结果，因此覆盖“检测”和“衡量”两层要求。
3. 将结果交给 CloudWatch 后，可以把群体差异与 15% 阈值绑定为告警，并在仪表板或周期报告中比较两个 Prompt。
4. 该组合把专门的评估工作交给托管能力，避免为每次响应编写解析、分组、统计和指标发布代码，所以符合“最少自定义开发”。

#### 逐项排除

- A. 能拼出自定义流水线，但必须自己定义公平性算法、解析输出并维护 Lambda，开发量不满足最少。
- B. Guardrails 的内容过滤与 `InvocationsIntervened` 反映安全干预，不是人口群体公平性指标。
- C. 正确；Clarify 负责偏差评估，CloudWatch 负责实时阈值、可视化和周期比较。
- D. 模型评估任务和调用日志能保留或比较样本，但不会自动成为按人口群体计算的实时公平性监控。

#### 解题方法

看到 fairness、bias、demographic groups，先找专门的偏差评估能力；看到 threshold、real time、weekly report，再找 CloudWatch 的指标、告警和可视化。不要把 Guardrail 的“拦截率”当成“公平性”。

### English

#### Exam focus and background

This question tests the boundary between fairness evaluation and safety filtering. The requirement is to measure whether recommendation outcomes differ across demographic groups and to compare two prompt approaches using the same measurement method. Counts such as latency, request volume, or the number of Guardrail interventions cannot establish whether one group receives systematically worse recommendations. The evaluator must calculate group-aware bias or fairness metrics from model outputs.

The operational requirements matter too: the company needs near-real-time visibility, an alarm when the discrepancy exceeds 15%, and a weekly comparison report. In the exam framing, SageMaker Clarify supplies the managed bias-analysis capability, while CloudWatch supplies metric visualization, threshold alarms, and reporting around those results. That division avoids maintaining a custom EventBridge/Lambda parser for every response and keeps both prompt variants on a consistent evaluation basis.

#### Analogy

Imagine a factory quality inspector calculating defect rates separately for three production lines, then wiring those rates to an alarm panel and a weekly report. The alarm panel does not perform the fairness calculation itself.

#### AWS service roles

| AWS service | Analogy role | Role in this question |
|---|---|---|
| Amazon SageMaker Clarify | Grouped quality inspector | Analyzes bias and fairness metrics by demographic group and prompt approach |
| Amazon CloudWatch | Dashboard and alarm panel | Receives metrics, evaluates the 15% threshold, and shows trends |
| Amazon Bedrock | Recommendation engine | Produces the outputs generated by the two prompt approaches |
| CloudWatch reporting path | Weekly editor | Supports recurring comparison of the two approaches |

#### Correct answer and reasoning

1. Identify the target metric: the stem asks for demographic fairness, not moderation or infrastructure health.
2. Use Clarify to analyze outputs across groups and produce bias/fairness measurements.
3. Publish or expose those results to CloudWatch so a 15% discrepancy can trigger an alarm and the two prompt variants can be compared over time.
4. This uses a managed evaluation capability instead of building custom parsing, grouping, statistics, and metric-publication code, satisfying the least-custom-development constraint.

#### Option-by-option elimination

- A. It can be made to work, but the custom output parser, fairness calculation, and metric pipeline create unnecessary development and maintenance.
- B. Guardrail filters and `InvocationsIntervened` measure safety interventions, not demographic fairness.
- C. Correct; Clarify evaluates bias, and CloudWatch handles alarms, dashboards, and recurring comparisons.
- D. Invocation logs and an evaluation job do not by themselves provide continuous, group-level fairness monitoring.

#### Exam strategy

For fairness, bias, and demographic-group wording, choose a bias-evaluation capability first. For thresholds and ongoing visibility, choose metrics and alarms. Always distinguish “the model was blocked” from “the model treated groups differently.”

## Question 2

### 中文

#### 考点背景

本题要求把三类控制放到最合适的 Guardrails 策略中。具体股票推荐、保证收益这类请求不是一个固定单词，而是具有语义和意图的高风险主题，应交给 Denied Topics；竞争对手名称则是明确的字符串，适合 Custom Word Filters，并且要在输入、输出两侧都 Block，防止用户诱导模型或模型主动提及竞争对手。

最后一条是 grounding。Grounding Score 越高，表示回答必须更有依据才能通过；题目要求回答基于公司批准的金融指导，所以需要较高阈值。低阈值会让缺乏证据的陈述更容易通过。解题时要把“语义主题、精确词、事实依据”分别映射到三种控制，不要用通用内容过滤器替代更精确的策略。

#### 场景比喻

像银行门口有三道门：意图门识别“请保证收益”，关键词门拦竞争者名字，证据门要求每句建议都拿得出内部手册依据。

#### AWS 服务角色

| AWS 服务 | 角色比喻 | 在本题中的作用 |
|---|---|---|
| Bedrock Guardrails Denied Topics | 意图门卫 | 阻止股票推荐、保证收益等高风险语义主题 |
| Custom Word Filters | 精确词闸 | 匹配竞争对手名称，并在输入和输出中 Block |
| Grounding Check | 证据审计员 | 用较高 Grounding Score 阈值限制无批准依据的声明 |
| Amazon Bedrock | 对话柜台 | 生成并接收需要被控制的金融对话 |

#### 正确答案与推理

1. 把高风险对话模式加入 Denied Topics，因为它们靠含义识别，不是简单词命中。
2. 把竞争对手名称加入 Word Filters，并把 input、output action 都设为 Block，覆盖双向内容流。
3. 提高 Grounding Score 阈值，让回答必须更充分地由批准的金融指导支撑。
4. 因此三项组合是 A、D、F，分别对应语义阻断、精确阻断和证据门槛。

#### 逐项排除

- A. 正确；Denied Topics 能表达“保证收益”和具体投资建议等语义风险。
- B. 通用内容过滤器不是表达金融业务主题禁用规则的最精确工具。
- C. 竞争对手名称是精确词匹配场景，内容过滤器不能可靠替代 Word Filter。
- D. 正确；自定义词过滤器在输入和输出都 Block，能阻止双向出现。
- E. 错误方向；低阈值放宽了对无依据回答的要求。
- F. 正确；高阈值提高了回答获得通过所需的事实依据水平。

#### 解题方法

先分类：意图/话题用 Denied Topics，固定字符串用 Word Filters，事实支撑用高 Grounding 阈值。多选题中，逐条检查输入和输出动作是否都覆盖，而不是只看 Prompt 端。

### English

#### Exam focus and background

The key is to map each policy to the Guardrails control that expresses it most precisely. A request for a specific stock recommendation or a guaranteed return is a semantic intent, not merely a single forbidden word, so Denied Topics is the natural control. A competitor name is an exact string, so a custom word filter can block it on both the input and output sides. That prevents a user from prompting the name and prevents the model from introducing it.

The grounding requirement is separate. A higher Grounding Score threshold makes the response pass only when it is better supported by the company’s approved financial guidance. A low threshold would relax that control and allow unsupported claims more easily. The exam pattern is therefore a three-way mapping: semantic topic, exact term, and evidence threshold. Do not substitute a broad harmful-content filter for a precise business-policy control.

#### Analogy

Think of a bank with three gates: an intent gate recognizes “guarantee my return,” a keyword gate stops competitor names, and an evidence gate asks every financial claim to cite the approved handbook.

#### AWS service roles

| AWS service | Analogy role | Role in this question |
|---|---|---|
| Bedrock Guardrails Denied Topics | Intent gatekeeper | Blocks semantic high-risk topics such as guaranteed returns |
| Custom Word Filters | Exact-word gate | Matches competitor names and blocks them in both directions |
| Grounding check | Evidence auditor | Uses a high score threshold for claims grounded in approved guidance |
| Amazon Bedrock | Conversation counter | Generates and receives the financial dialogue being controlled |

#### Correct answer and reasoning

1. Put high-risk conversation patterns in Denied Topics because the rule depends on meaning and intent.
2. Put competitor names in a custom word filter and block both inputs and outputs so neither side can introduce them.
3. Use a high grounding threshold so unsupported statements about the company’s approved guidance do not pass easily.
4. The combination is therefore A, D, and F: semantic blocking, exact blocking, and a stricter evidence requirement.

#### Option-by-option elimination

- A. Correct; Denied Topics expresses semantic risks such as guaranteed returns and stock recommendations.
- B. A general content filter is less precise than a denied topic for this financial-policy rule.
- C. Competitor names are an exact-match use case, so a word filter is more reliable.
- D. Correct; blocking on both input and output covers the complete content path.
- E. Incorrect direction; a low threshold makes unsupported claims easier to accept.
- F. Correct; a high threshold demands stronger grounding in approved guidance.

#### Exam strategy

Classify the requirement before choosing the feature: intent means Denied Topics, literal text means Word Filters, and evidence means a high grounding threshold. In multi-select questions, verify the action and the direction of enforcement as well as the feature name.

## Question 3

### 中文

#### 考点背景

这里的瓶颈不是模型“算错”，而是同步链路把较长的生成过程当成一次必须完整结束的 HTTP 请求。React 前端经过 AppSync，再由 Lambda resolver 以 `RequestResponse` 调用知识库；复杂问题需要更长时间，用户就会在结果尚未完成时遇到超时或长时间白屏。改善体验的关键是尽早发送已经生成的片段，而不是单纯把等待上限调大。

AWS Amplify AI Kit 的价值在于把流式交互接到现有 GraphQL/客户端体验中，让内容边生成边渲染，同时保留知识库问答的语义。不能为了“流式”就把 `RetrieveAndGenerate` 换成普通模型流式 API；那会改变知识库检索路径。队列适合异步作业，不适合用户正在等待连续回答的交互场景。

#### 场景比喻

像厨师把汤一锅煮完才端出，顾客等到超时；流式方案像先端出已经煮好的第一勺，后面继续添汤，等待立刻变得可感知且有进展。

#### AWS 服务角色

| AWS 服务 | 角色比喻 | 在本题中的作用 |
|---|---|---|
| AWS Amplify AI Kit | 前台传菜系统 | 将生成内容以流式体验交给 React 客户端并优化渲染 |
| AWS AppSync | GraphQL 服务台 | 承载前端与后端之间的实时交互接口 |
| Lambda resolver | 厨房接单员 | 调用知识库问答后端，避免把全部结果才返回的阻塞体验 |
| Bedrock Knowledge Bases | 菜谱与资料库 | 为回答提供检索增强的企业资料上下文 |

#### 正确答案与推理

1. 超时集中在复杂问题，说明同步完整响应的关键路径过长，而不是偶发错误。
2. 题目要改善用户体验，必须让用户先看到增量结果；只提高 timeout 不会降低感知等待。
3. Amplify AI Kit 针对现有 Amplify/AppSync/React 组合提供流式响应和客户端渲染支持。
4. 它保留 `RetrieveAndGenerate` 的知识库交互语义，因而同时处理性能体验和功能约束。

#### 逐项排除

- A. 正确；在现有 GraphQL 应用中引入流式响应，减少同步阻塞和长时间白屏。
- B. 延长 timeout 与重试只让失败更晚发生，也可能放大负载，不能提供首个片段。
- C. SQS 会把问答改成异步任务，难以自然地把连续答案实时交回当前用户。
- D. 普通模型流式 API 不等同于知识库的 `RetrieveAndGenerate`，还引入额外 WebSocket 开发。

#### 解题方法

看到长生成、用户等待、超时和“提升体验”，优先找 streaming 与 time-to-first-token。看到 Knowledge Bases/`RetrieveAndGenerate`，不要用会丢失检索语义的替换方案。

### English

#### Exam focus and background

The bottleneck is the synchronous request path, not necessarily incorrect model reasoning. The React client calls AppSync, the Lambda resolver uses a `RequestResponse` invocation, and a complex knowledge-base question keeps the request open until the answer is complete. That creates timeout pressure and a blank or stalled interface. The useful improvement is to deliver partial output as it becomes available instead of merely increasing the maximum wait.

Amplify AI Kit fits the existing Amplify, AppSync, and React interaction model by enabling a streaming user experience and progressive client rendering. Streaming should not be confused with replacing the knowledge-base operation with a generic model streaming action. That would change the retrieval semantics. SQS is useful for asynchronous work, but an interactive assistant needs a response path that keeps the user informed while the answer is being generated.

#### Analogy

It is the difference between a chef serving an entire soup pot only after it is finished and serving the first ladle immediately while the rest continues cooking.

#### AWS service roles

| AWS service | Analogy role | Role in this question |
|---|---|---|
| AWS Amplify AI Kit | Front-of-house delivery system | Provides streaming interaction and client-side progressive rendering |
| AWS AppSync | GraphQL service desk | Carries the application’s interactive API exchange |
| Lambda resolver | Kitchen order handler | Connects the GraphQL request to the knowledge-base operation |
| Bedrock Knowledge Bases | Recipe and reference library | Supplies retrieved context for the grounded answer |

#### Correct answer and reasoning

1. More frequent failures on complex questions indicate an overly long synchronous critical path.
2. The user-experience requirement calls for early incremental output, not only a larger timeout.
3. Amplify AI Kit addresses streaming in the existing Amplify/AppSync/React pattern and supports progressive rendering.
4. It preserves the knowledge-base interaction instead of replacing `RetrieveAndGenerate` with an unrelated generic model API.

#### Option-by-option elimination

- A. Correct; it adds incremental GraphQL delivery and reduces the visible cost of a long generation.
- B. A longer timeout and retries delay failure but do not improve time to first output.
- C. SQS turns the interaction into an asynchronous job and does not naturally stream the answer to the waiting user.
- D. A generic model-streaming API changes the knowledge-base path and adds unnecessary WebSocket work.

#### Exam strategy

When the stem emphasizes long generation, timeouts, and user experience, look for streaming and early output. When it names a knowledge-base API, preserve that retrieval contract unless the question explicitly asks for a redesign.

## Question 4

### 中文

#### 考点背景

本题把“代码中的决策逻辑”和“经常变化的路由配置”分开考。用户等级、金额、合规区域和每小时成本是业务规则，可能频繁改变；模型 ID、区域和 A/B 流量比例是配置数据。理想方案让 Lambda 保留可测试的决策代码，却从 AppConfig Agent 读取已发布配置，因而调整规则不需要重新部署函数。

单一 API Gateway 入口也很重要：所有请求先进入相同的扩展、认证和观测边界，再由 Lambda 选择适当 FM。AppConfig Agent 负责把配置带到计算环境附近并刷新，Lambda 负责解释规则；不要把授权器、Stage Variables 或环境变量当成完整的动态业务规则引擎。

#### 场景比喻

像机场保留同一套值班流程，却把“哪个航班进哪个登机口”的电子指示牌做成可实时更新；改指示牌不必重建机场，也不该让门卫兼任调度中心。

#### AWS 服务角色

| AWS 服务 | 角色比喻 | 在本题中的作用 |
|---|---|---|
| AWS AppConfig Agent | 可刷新规则牌 | 向 Lambda 提供动态、集中发布的路由配置 |
| AWS Lambda | 业务调度员 | 按用户、金额、区域、成本和 A/B 规则选择 FM |
| Amazon API Gateway | 统一入口 | 暴露单一 API endpoint，承接并扩展请求 |
| Amazon Bedrock | 多个目的地 | 承载被路由到的不同 foundation model |

#### 正确答案与推理

1. 题干明确要求无需部署新代码，因此规则不能只放在 Lambda 环境变量或代码中。
2. AppConfig Agent 让函数读取已发布且可刷新的配置，适合每小时变化并需要快速传播的规则。
3. 复杂条件仍由 Lambda 业务逻辑执行，能表达用户等级、交易额、监管区域和实时成本的组合。
4. 单一 API Gateway endpoint 统一入口，Lambda 再选择不同 Bedrock FM，所以 C 同时满足动态性、复杂性和扩展性。

#### 逐项排除

- A. 环境变量变更需要更新函数配置并等待传播，不适合高频、集中治理的规则刷新。
- B. 映射模板和 Stage Variables 更适合简单映射，难以维护复杂实时业务判断。
- C. 正确；AppConfig 提供动态配置，Lambda 执行决策，单一入口降低编排开销。
- D. Authorizer 的主职责是授权，把路由塞进授权上下文并为每个 FM 建函数会扩大维护面。

#### 解题方法

看到“规则频繁变、无需部署、集中传播”，把配置放 AppConfig，把判断放 Lambda。看到“单一入口”，优先避免每个模型一套独立 API 和函数链。

### English

#### Exam focus and background

This question separates business decision logic from frequently changing routing configuration. User tier, transaction value, regulatory zone, hourly cost, model IDs, and traffic allocations are data that may change independently of the code. The desired design keeps a testable decision function in Lambda while allowing the function to read centrally published configuration through the AppConfig Agent. A rule change therefore does not require a code deployment.

The single API Gateway endpoint is also meaningful: requests enter one consistent boundary for authentication, scaling, and observability, then Lambda selects the appropriate Bedrock model. The AppConfig Agent handles nearby retrieval and refresh of configuration; Lambda interprets the rules. Environment variables, stage variables, and an authorizer are not substitutes for a dynamic business-routing configuration system.

#### Analogy

An airport keeps the same operating procedures but uses a live gate display to assign flights. Updating the display should not rebuild the airport, and the security guard should not become the air-traffic controller.

#### AWS service roles

| AWS service | Analogy role | Role in this question |
|---|---|---|
| AWS AppConfig Agent | Refreshable rule board | Delivers centrally managed, dynamic routing configuration to Lambda |
| AWS Lambda | Business dispatcher | Applies user, value, Region, cost, and A/B rules to select an FM |
| Amazon API Gateway | Common entrance | Exposes one scalable endpoint for the application |
| Amazon Bedrock | Set of destinations | Hosts the foundation models selected by the routing decision |

#### Correct answer and reasoning

1. The no-deployment requirement means the rules cannot live only in code or Lambda environment variables.
2. The AppConfig Agent supplies refreshed, published configuration suitable for rules that change frequently.
3. Lambda retains the complex proprietary logic needed to combine tier, transaction, compliance, cost, and experiment conditions.
4. One API Gateway endpoint provides a common entry while Lambda selects the required Bedrock FM, so C covers all constraints.

#### Option-by-option elimination

- A. Environment-variable updates are function configuration changes and are a poor fit for high-frequency centralized refresh.
- B. Mapping templates and stage variables are better for simple mappings than complex, rapidly changing business decisions.
- C. Correct; AppConfig supplies dynamic data, Lambda makes the decision, and one endpoint limits orchestration overhead.
- D. An authorizer should enforce authorization; using it for routing and creating one function per FM expands the maintenance surface.

#### Exam strategy

For “change rules without redeploying,” separate configuration from code and look for AppConfig. For complex proprietary conditions, keep the decision in compute code. For a unified entry point, favor one API boundary over model-specific chains.

## Question 5

### 中文

#### 考点背景

这道题考“内容生成控制平面”的集中治理。文档摘要、风险分类和待复核术语是所有部门共享的输出契约；法务、人力资源、财务的语气则是可管理的 Prompt 变体。Prompt Management 适合集中保存可复用模板和变体，避免每个团队在 DynamoDB 或代码里维护一份近似但不完全相同的模板。

审核要求也应留在托管的 Guardrails：类别过滤器处理仇恨或不适当主题，敏感信息/词语策略处理个人健康信息等内容。这样调整审核标准只改 Guardrail 配置，不必修改后处理 Lambda、Step Functions 流程或 Comprehend 集成。题眼是 least maintenance overhead，而不是“任何能拼起来的架构”。

#### 场景比喻

像总部印制一套统一报告表，给每个部门发不同语气的封面；保安在总入口按同一套禁带清单检查，而不是每个部门自己养一支检查队。

#### AWS 服务角色

| AWS 服务 | 角色比喻 | 在本题中的作用 |
|---|---|---|
| Bedrock Prompt Management | 模板档案室 | 集中管理共享模板和部门 Prompt 变体 |
